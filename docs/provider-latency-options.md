# Autocomplete latency: API options

Research date: 25 October 2026. Keep Gemini, Tiger Data and Snowflake for the hackathon. This memo changes no providers or model IDs. External-provider experiments below require the user's approval before implementation.

## What the evidence says

**Measured baseline:** the nine-request [baseline evidence](evidence/latency-baseline.json) has a 4.42-second median and 6.42-second maximum. These figures describe this app and run, not provider guarantees. The original four dependent provider stages—tags, embeddings, judging, generation—accumulated round-trip and inference time before the user saw anything. See [final performance results](performance.md) for the optimized comparison.

**Code inspected:** the initial implementation used `gemini-3.5-flash-lite` for tags/judges, `gemini-3.6-flash` for generation, and `gemini-embedding-001` for retrieval. Generation requested `thinking_level="low"`; judges used `minimal`. Generation required the fields for both autocomplete and questions, including empty unused fields. AI/API logs were already scheduled in the background; trace persistence and knowledge use-count updates remained on the response path. The SDK client was already reused. These are observations of the starting implementation; see the optimization changes and their benchmark results for the final implementation.

**Inference:** changing vendors alone cannot remove the serial pipeline or application waiting time. Prioritize fewer repeated calls, shorter outputs, cancellation, and bounded in-memory caches. A subsecond cold, fully grounded request is a target to test, not a promise supported by the baseline.

## Sponsor-preserving priorities

| Priority | Change to evaluate | Why it fits this application | Evidence / constraint |
|---|---|---|---|
| 1 | Reuse exact responses and tag embeddings; coalesce identical in-flight work | Repeated editor states and recurring tags should not pay again for identical inference | Application design recommendation. Response reuse must include cursor, settings, knowledge version and model configuration; rebuild request ID/revision for each caller. Bound caches by size and TTL and keep prompt text ephemeral. Embedding keys include model, dimensions and task type. |
| 1 | Cancel obsolete generation and remove database log writes from the response path | Keystrokes make old suggestions useless; analytics should not delay the visible result | Application design recommendation. Preserve metadata logging through a bounded queue and shutdown flush; never silently discard correctness-critical writes. A caller cancellation must not cancel shared work still needed by another caller. |
| 1 | Use a smaller internal response shape for autocomplete; stop generating unused explanations | A short suffix should not decode question/edit fields or judge reasons that the application never consumes | Keep the public response contract and validation. Reducing decoded output and serial requests is also recommended in [OpenAI's general latency guide](https://developers.openai.com/api/docs/guides/latency-optimization); its quantitative heuristics are not Gemini benchmarks. |
| 2 | A/B test generation at `thinking_level="minimal"` using the same model | The task is a short grounded continuation, often requiring little deliberation | Google documents `minimal` support for 3.6 Flash and 3.5 Flash-Lite. It may still perform some thinking. A tiny `max_output_tokens` is not a substitute: that limit includes thought tokens and can truncate JSON. [Gemini thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking) |
| 2 | Review candidates together, or combine review and generation with explicit per-candidate decisions | Reduces request fan-out or removes a serial stage while retaining model review of each candidate | Hypothesis requiring quality evaluation. A batched judge alone reduces call count but is not guaranteed faster than parallel judges; a longer batch may decode more tokens. Do not replace relevance review with keyword overlap. |
| 3 | Benchmark `google-genai[aiohttp]` against the current transport | The lockfile at inspection contained `google-genai` 2.33.0 and `httpx`, without `aiohttp` | Google documents the extra as its faster async-client option. Keep a long-lived client; measure warm and cold calls. Transport savings cannot be assumed to remove provider inference time. [Official Python SDK](https://googleapis.github.io/python-genai/) |
| 3 | Add streaming if time to first useful suffix remains materially better than total generation | Makes progress visible before all output finishes | Gemini supports streaming structured output. Chunks are partial JSON; schema key order controls output order. Put the discriminant and suffix early, parse incrementally, and preserve final validation and stale-revision checks before accepting edits. Streaming does not eliminate the preceding retrieval chain. [Structured output](https://ai.google.dev/gemini-api/docs/generate-content/structured-output) |

Do not reuse old relevance decisions based only on a broad topic signature: adding “do not use React” to a React-related draft changes meaning without necessarily changing its broad topic. Exact caches are safer; broader reuse needs explicit invalidation and evidence that quality is preserved. Likewise, accepting a typed-through prefix of an already displayed suffix can be immediate, provided the remainder still belongs to the exact displayed suggestion and cursor snapshot.

## Gemini features to approach selectively

**Context caching is unlikely to be the first win.** Google's current generateContent documentation sets the minimum at 4,096 input tokens for 3.6 Flash. The recorded application request uses about 2,500 input tokens across *all* calls; that is not 4,096 tokens in the generation call. Keep stable content before changing draft text, but inspect cached-token usage rather than assuming a hit. Do not inflate prompts to qualify. The cited table does not state a 3.5 Flash-Lite minimum, so verify that separately before relying on it. [Gemini context caching](https://ai.google.dev/gemini-api/docs/generate-content/caching)

**Priority inference is an optional sponsor-preserving experiment.** Google documents its preview Priority tier for both current text models, using the Interactions API and `service_tier="priority"`. It advertises lower latency at a 75–100% premium, can downgrade requests to Standard, and describes latency in seconds. This is not evidence of subsecond autocomplete. The application uses generateContent, so endpoint/SDK compatibility and a migration need evaluation; do not assume adding a configuration field to the existing wrapper works. Record the returned service tier during tests. [Gemini Priority inference](https://ai.google.dev/gemini-api/docs/priority-inference)

Batch and Flex are intended for latency-tolerant work. They are possible tools for offline evaluation or ingestion, not interactive ghost text. [Gemini optimization options](https://ai.google.dev/gemini-api/docs/optimization)

## Alternative providers: research only

All alternatives below are **documented capabilities, not tested integrations or measured wins**. Benchmark the actual short suffix and question tasks before selecting one. Published tokens/second largely describes decoding; a 25-word suffix can be dominated by network, queuing, prefill and reasoning. Compare client-observed time to first useful output and complete validated response, not token speed alone.

| Candidate | Why benchmark it after approval | Constraints to test |
|---|---|---|
| Cerebras, `qwen-3.8-27b` and `gpt-oss-120b` | Its shared-inference catalog advertises approximately 1,850 and 3,000 tokens/second respectively. Treat these as vendor claims. [Model catalog](https://inference-docs.cerebras.ai/models/overview) | Both document strict structured outputs; strict schemas require `additionalProperties: false`. Streaming is documented separately, so verify the exact streaming/schema combination. Measure reasoning overhead, useful-suffix quality and rate-limit behavior. [Structured output](https://inference-docs.cerebras.ai/capabilities/structured-outputs), [streaming](https://inference-docs.cerebras.ai/capabilities/streaming) |
| Groq, `openai/gpt-oss-20b` | Its production catalog advertises approximately 1,000 tokens/second. This is a sensible compact-model comparison, not an end-to-end latency result. [Models](https://console.groq.com/docs/models) | Strict structured outputs are supported, but current documentation says structured outputs cannot stream. JSON-object mode has weaker guarantees. Retain application validation even with strict JSON. [Structured output](https://console.groq.com/docs/structured-outputs) |
| OpenAI, `gpt-6-luna` with `reasoning.effort="none"` | Current docs position it for focused high-volume tasks and list streaming and structured outputs. [Model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna) | No application-specific latency measured. Compare Standard and Fast only if needed; provider/model changes remain approval-gated. Predicted Outputs principally helps when much of the desired output is already known, so it is not an obvious fit for an unknown short suffix. [Latency guide](https://developers.openai.com/api/docs/guides/latency-optimization) |

Avoid stale model recommendations: Groq's Llama 3.1 8B and Llama 3.3 70B are no longer generally available on its free/developer tiers; committed enterprise accounts are excepted. [Groq deprecations](https://console.groq.com/docs/deprecations)

## Benchmark that can decide this

Use the same representative draft set, knowledge snapshot, settings and client region. Separate cold first requests, warm exact-repeat requests, appended text, topic changes, cursor moves and active typing that cancels requests. Randomize A/B order and report sample counts. Collect median and p95 latency, first useful suffix time, complete validated-response time, input/output/thinking/cached tokens, error/timeout rate, schema failures, cancellations and application/provider cache hits.

Keep quality beside speed: suffix-only behavior, partial-word joining, UTF-16 correctness, no invented project facts, relevant knowledge usage, valid question edits and correct `none` decisions. Use metadata-only persistent logging. Save neither user drafts nor knowledge bodies in benchmark logs. A faster response that is invalid, stale or irrelevant does not count as a successful autocomplete.
