# Retrieval and storage latency audit

Research date: 25 October 2026. Scope: the current working tree, existing benchmark files, the root agent's read-only live Tiger diagnostics, and primary provider/research sources. No application code, provider configuration, schema, or stored data was changed by this research.

## Conclusion

The main problem is the synchronous application dependency chain. For a fresh draft, Gemini tag inference must finish before Gemini embedding, which must finish before Tiger retrieval, which must finish before the combined Gemini review/generation call. A read-only SQL experiment also found a concrete, fixable query representation problem: median execution fell from 89.84 ms to 1.52 ms when the same vectors entered SQL as `vector[]` instead of repeatedly cast `text[]`. Tiger network time remains meaningful, but optimizing the database alone cannot make the current request path subsecond. Snowflake is not on that path.

The most promising sponsor-preserving redesign is to prepare a versioned retrieval view before the user pauses typing, use cheap local candidate selection on the interactive path, and spend at most one Gemini generation call there. Tiger remains the authoritative knowledge/vector store; Gemini still performs ingestion, embedding, and generation; Snowflake remains the offline evaluation/training system. All expected savings from that redesign remain experiments, not measured results.

## What the measurements establish

The latest [linked incremental run](/Users/mattlo/Desktop/oxhack-2026/docs/evidence/latency-edits-linked.json:1) contains nine sequential in-process requests, three initial drafts and six edits, against the expanded corpus. Its median is 2,225 ms. The following values were recomputed directly from its nine samples; shares use aggregate elapsed time, not sums of medians.

| Component | Mean per request | Share of total recorded time |
|---|---:|---:|
| Gemini tag stage | 783.6 ms | 34.4% |
| Retrieval stage, including embedding | 350.6 ms | 15.4% |
| Combined review/generation | 1,054.8 ms | 46.3% |
| Time outside named spans | 88.4 ms | 3.9% |

Three requests reused knowledge and recorded zero retrieval time. The nine retrieval values range from zero to 742 ms. These spans combine cache lookup, Gemini embedding, pool acquisition, serialization, network, SQL, and result decoding; they are not measurements of Tiger execution alone. The timer starts before `retrieve()` in [run.py:50](/Users/mattlo/Desktop/oxhack-2026/backend/app/pipeline/run.py:50), while embedding occurs inside [retrieve.py:111](/Users/mattlo/Desktop/oxhack-2026/backend/app/pipeline/retrieve.py:111).

Subtracting the *entire* retrieval span from each recorded request produces a counterfactual median of **1,812 ms**, even assuming zero-cost replacement with identical output. The earlier nine-request [HTTP incremental run](/Users/mattlo/Desktop/oxhack-2026/docs/evidence/latency-incremental.json:1) gives **1,690 ms** under the same calculation. These are arithmetic bounds on these samples, not forecasts. Removing SQL alone saves less than removing the whole retrieval span.

The [live diagnostics](/Users/mattlo/Desktop/oxhack-2026/docs/evidence/latency-audit-diagnostics.json:1) confirm 61 stored tags, 29 knowledge items, and 200 ms configured editor delay. Eight warm `SELECT 1` calls have 85.875 ms median; a fresh connection took 841.18 ms in this saved run. Connection setup is not paid for every request because a pool already exists. The root agent then compared three SQL shapes in randomized order, four observations each, using the same four stored tag vectors:

| SQL shape | Median server execution | Median client EXPLAIN duration |
|---|---:|---:|
| Current `text[]`, casting `q.v::vector` inside scan | 89.84 ms | 200.00 ms |
| Input cast once to `vector[]`; direct `q.v` | 1.52 ms | 91.23 ms |
| Materialized converted-vector CTE | 1.82 ms | 93.15 ms |

All twelve fixture results matched after canonicalizing candidate order. Both alternatives strongly support repeated text-to-vector conversion as the explanation, although no function-level profiler was run. This is an approximately 88 ms server-side improvement on a small fixture, not a production latency guarantee or a reason to claim the whole application is 59× faster. The scan still visits 61 tags per vector: an index change was unnecessary. The reproducible script is [collect-latency-diagnostics.py](/Users/mattlo/Desktop/oxhack-2026/docs/research/collect-latency-diagnostics.py).

Historical successful AI calls in the diagnostics have means of 771.9 ms for tags (78 calls), 275.0 ms for query embedding (60), and 1,037.8 ms for generation (87). These include tests and varied requests and must not be combined into a synthetic production distribution. They support the order of magnitude of the bottlenecks, not a controlled provider comparison.

The repository benchmark's nearest-rank `p95` is the maximum for nine samples: [bench_enhance.py:42](/Users/mattlo/Desktop/oxhack-2026/backend/scripts/bench_enhance.py:42). Its in-process runs exclude HTTP transport; all benchmark runs exclude editor debounce and paint. The first linked sample also has 513 ms outside named stages. Settings refresh is a plausible contributor, but the current spans cannot attribute that residual conclusively.

| 3 | Reduce returned bodies or precompute retrieval excerpts | SQL fetches up to five × 8,000 body characters, but generation consumes at most five × 1,200-character excerpts | Compare metadata/excerpt snapshots to current bodies for actual answer quality. | 3 | Add single-flight for identical embedding/retrieval work | TTL caches do not coalesce concurrent misses | Test simultaneous identical misses and cancellation of one caller. | 4 | Consider pgvectorscale or more index tuning only after corpus growth or measured server bottlenecks | HNSW already exists; the current corpus has only 61 tag vectors | Compare exact scan, HNSW and StreamingDiskANN at equal recall with realistic data volume. The stored-tag preload is a narrowly scoped improvement even before redesigning retrieval. A known tag has the same text embedding input as the stored tag, provided model, dimensionality, preprocessing and task match. Query tags absent from the vocabulary still require the current fallback. Precomputed nearest-tag neighborhoods can remove repeated work for known tags, but deleting nearby synonyms from the candidate set would change recall.

The larger redesign must not treat lexical overlap as proof of relevance. It should return a bounded candidate superset and retain Gemini review against the current draft. A final review can reject irrelevant candidates, but cannot recover relevant documents that candidate selection omitted; evaluate recall explicitly. A hybrid selector can union exact tags, indexed lexical matches and available dense candidates without a separate model reranker. PostgreSQL documents GIN as its preferred full-text index, while pgvector documents hybrid retrieval and rank fusion. These describe building blocks, not a latency guarantee. [PostgreSQL full-text indexes](https://www.postgresql.org/docs/16/textsearch-indexes.html), [pgvector hybrid search](https://github.com/pgvector/pgvector#hybrid-search)

## Provider and architecture details

**Tiger indexes.** The active inner query uses ascending distance plus `LIMIT`, which is the index-compatible shape, and its cosine operator matches the declared HNSW operator class. A sequential scan over a tiny table is not evidence of a broken index. pgvector explicitly notes that small-table scans can be faster. Compare exact and approximate recall before tuning. StreamingDiskANN adds disk-oriented search, quantization and label filtering; it does not remove a cross-region round trip or an upstream embedding call. [pgvector troubleshooting](https://github.com/pgvector/pgvector#troubleshooting), [pgvectorscale](https://github.com/timescale/pgvectorscale)

**Pool behavior.** `min_size=1` means bursts may wait for existing connections or newly established ones. Monitor Psycopg's `requests_waiting`, `requests_wait_ms`, `connections_ms` and pool availability before resizing. Its documentation also warns that a connection health check adds network time. A second provider-side pooler is not automatically faster than the existing persistent app pool; Tiger's PgBouncer primarily addresses numerous short-lived client connections. [Psycopg pooling](https://www.psycopg.org/psycopg3/docs/advanced/pool.html), [Tiger connection pooling](https://d1ovb29l12vjqm.cloudfront.net/use-timescale/latest/services/connection-pooling/)

**Hidden shared-capacity risks.** [writers.py:51](/Users/mattlo/Desktop/oxhack-2026/backend/app/observability/writers.py:51) creates an unbounded set of metadata-write tasks. [trace.py:65](/Users/mattlo/Desktop/oxhack-2026/backend/app/pipeline/trace.py:65) blocks the request when 256 trace tasks are pending. Ingestion holds a borrowed connection during remote tag generation and embedding at [ingest.py:32](/Users/mattlo/Desktop/oxhack-2026/backend/app/knowledge/ingest.py:32) and [ingest.py:54](/Users/mattlo/Desktop/oxhack-2026/backend/app/knowledge/ingest.py:54). These are credible concurrency/outage tail risks, not established explanations of today's sequential two-second samples. Activity stats and detail reads also perform several serial SQL round trips, but they are separate endpoints: [stats.py:48](/Users/mattlo/Desktop/oxhack-2026/backend/app/activity/stats.py:48), [logs.py:49](/Users/mattlo/Desktop/oxhack-2026/backend/app/activity/logs.py:49).

**Freshness.** All current cache generations and pending-trace rows are process local. Adding workers without a shared knowledge version/invalidation protocol makes them disagree. A local mirror needs atomic snapshot swaps after committed mutations, model/task provenance, deletion invalidation, and a measured staleness bound. Tiger read replicas use asynchronous replication and introduce their own lag; read scaling is not automatically a geographically local cache. [Tiger read scaling](https://docs.tigerdata.com/use-timescale/latest/ha-replicas/read-scaling)

**Embedding configuration.** Current matching is tag-to-tag semantic similarity, using 768-dimensional `gemini-embedding-001`: [gemini.py:71](/Users/mattlo/Desktop/oxhack-2026/backend/app/llm/gemini.py:71). The schema stores no model/task identifier alongside vectors. If redesigned to prompt-to-document retrieval, evaluate `RETRIEVAL_QUERY`/`RETRIEVAL_DOCUMENT` and rebuild the corpus coherently; changing only the query task is unsound. A switch to Gemini Embedding 2 is not a drop-in speed improvement: Google documents incompatible spaces, different task instructions and different multi-input aggregation semantics. Lower dimensions trade storage/computation and quality; they do not eliminate network time. Cosine distance is scale invariant, so missing explicit unit normalization is not itself proof that this cosine-based implementation is wrong. [Gemini embedding documentation](https://ai.google.dev/gemini-api/docs/embeddings)

**Snowflake.** [export.py:31](/Users/mattlo/Desktop/oxhack-2026/backend/app/analytics/export.py:31) exports outcomes; [train.py:48](/Users/mattlo/Desktop/oxhack-2026/backend/app/analytics/train.py:48) runs classification training in a worker thread; neither is called by `run_enhance`. The current model is trained and evaluated but is not used to gate autocomplete. Keep Snowflake useful for evaluating candidate-selection quality, acceptance, latency/error slices, and offline routing-policy experiments. Do not move a Snowflake SQL prediction call onto every keystroke. The built-in classifier's documented interface is a warehouse-backed model object; exporting it directly for local inference is not established here. [Snowflake classification](https://docs.snowflake.com/en/user-guide/ml-functions/classification)

## Research: mechanisms worth adapting, with limits

| Primary source | Relevant mechanism | Applicability here |
|---|---|---|
| [PipeRAG, 2024](https://arxiv.org/html/2403.05676v1) | Overlap retrieval with generation using prefetched context and tune retrieval intervals. Reports up to 2.6× in its evaluated setup. | Useful motivation to separate retrieval from generation scheduling. It studies periodic retrieval with Retro-style models; the first retrieval remains a dependency. This application makes a short closed-API completion, so the published speedup does not transfer directly. |
| [Predictive Prefetching for RAG, ICML 2026](https://arxiv.org/html/2605.17989v1) | Predict upcoming retrieval needs using model signals, maintaining asynchronous context. Reports up to 43.5% end-to-end and 62.4% TTFT reduction. | The paper explicitly requires hidden states, attention and value vectors; this rules out directly transplanting its main method into the current Gemini API wrapper. Adapt the scheduling idea using observable draft revisions and edit timing, not claims of equivalent internal prediction. |
| [When Does Streaming Tool Use Help?, June 2026 preprint](https://arxiv.org/html/2606.20113v2) | Measures when retrieval intent stabilizes during incoming input. Retrieval can finish while the user continues typing. | Closest architectural fit: independently prefetch likely candidates before the final quiet-time trigger. Its clean uniform word streams, CRAG task, coarse top-result stability and favorable grounding subset limit numerical transfer. Measure this app's actual edit streams, late negations, topic switches and wasted prefetch cost. |
| [Cursor security: codebase indexing](https://www.cursor.com/security) | Documents incremental codebase change detection and server-side embedding/indexing. | Supports moving stable-source preparation out of the request path. It does not disclose the complete Cursor Tab serving path and is not evidence that Tab performs this application's sequence of model calls. |

Prefetch must be bounded, cancel obsolete candidate work, retain source revision/version, and never display unvalidated speculative content. The current implementation only remembers **completed** request contexts, [context.py:52](/Users/mattlo/Desktop/oxhack-2026/backend/app/pipeline/context.py:52); that is caching past work, not preparing likely future context while the user is still editing. Measure the percentage of requests with fresh useful candidates ready at trigger time and the extra work per accepted suggestion.

## Limits of this audit

No application load test, provider migration, new paid inference run, replica creation, or index/schema mutation was performed by this subtask. The root agent's live probes are read-only and the full saved diagnostics are the evidence authority. Timing decomposition, local candidate selection, preloading and prefetch still need controlled A/B evaluation. The SQL representation experiment is measured, but needs implementation and broader correctness validation. At this small scale, pursue fewer blocking model calls and less network waiting before committing to a more elaborate vector database index.
